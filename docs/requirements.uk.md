# Бронювання переговорних — специфікація вимог

> Джерело: технічне завдання UA-Skills · event2 (конкурс для junior-розробників).
> Цей документ — структурована й пронумерована версія вимог для подальшої роботи над проєктом.
> Версія 1.1 · 2026-07-27

---

## 1. Мета проєкту

Невеликий веб-застосунок для бронювання переговорних кімнат в офісі. Співробітник відкриває розклад кімнати, бачить зайняті слоти та бронює вільний час. Своє бронювання можна скасувати; чужі бронювання чіпати не можна (ні через UI, ні через API).

## 2. Ролі

| Роль | Опис |
|---|---|
| Гість | Неавтентифікований відвідувач. Доступні лише реєстрація та вхід; увесь інший застосунок — за логіном (див. DEC-1) |
| Користувач | Зареєстрований співробітник. Переглядає розклад усіх кімнат, створює бронювання, редагує та скасовує **лише свої** бронювання |
| Адміністратор | **Відсутній.** Кімнати створюються сідом, окрема адмінка не потрібна |

## 3. Глобальні домовленості (константи домену)

| Параметр | Значення |
|---|---|
| Офісний часовий пояс | `Europe/Kyiv` |
| Робочі години | 09:00–19:00 **за часом офісу**, однакові для всіх кімнат |
| Крок сітки / кратність часу | 30 хвилин |
| Мінімальна тривалість бронювання | 30 хвилин |
| Максимальна тривалість бронювання | 4 години |
| Зберігання часу в БД | UTC |
| Відображення часу в UI | Часовий пояс користувача (визначається з браузера) |
| Валідація робочих годин | Завжди за часом офісу, незалежно від пояса користувача |
| Перший день тижня в сітці | Понеділок за замовчуванням, конфігурується (див. DEC-2) |

## 4. Функціональні вимоги

### FR-1. Автентифікація

- **FR-1.1** Реєстрація з полями: ім'я, email, пароль.
- **FR-1.2** Вхід (email + пароль) і вихід.
- **FR-1.3** Сесія зберігається після перезавантаження сторінки (persist session: cookie/сесія/токен — на вибір).
- **FR-1.4** Email унікальний. Унікальність перевіряється **без урахування регістру** та **зайвих пробілів по краях**: `Ivan@x.com` і `ivan@x.com` — одна адреса. (Практично: нормалізувати `trim().toLowerCase()` перед збереженням і порівнянням.)
- **FR-1.5** Ім'я: непорожнє; відображається в розкладі як автор бронювання; унікальність **не** вимагається.
- **FR-1.6** Пароль: від 8 до 72 символів; вимог до складу немає. (72 — верхня межа bcrypt.)
- **FR-1.7** Усі перевірки виконуються **на сервері**; помилки показуються користувачу зрозумілим повідомленням.

### FR-2. Кімнати

- **FR-2.1** 5–6 переговорних створюються сідом. Атрибути: назва, поверх, місткість.
- **FR-2.2** CRUD-адмінка для кімнат не потрібна.
- **FR-2.3** Робочі години в усіх кімнат однакові: 09:00–19:00 за часом офісу (`Europe/Kyiv`).

### FR-3. Розклад кімнати (тижнева сітка)

- **FR-3.1** Сітка на тиждень: дні по горизонталі, час по вертикалі, слоти по 30 хвилин.
- **FR-3.2** Зайняті слоти видно всім користувачам: відображаються **назва бронювання** та **хто забронював** (ім'я автора).
- **FR-3.3** Навігація тижнями: вперед і назад (без обмеження глибини в ТЗ).
- **FR-3.4** Орієнтир вигляду: тижневий вид Google Calendar.
- **FR-3.5** Сітка верстається самостійно (таблиця або CSS grid); готові календарні компоненти заборонені (див. TECH-5).

### FR-4. Часовий пояс користувача

- **FR-4.1** Увесь час в інтерфейсі відображається в часовому поясі користувача, визначеному з браузера (`Intl.DateTimeFormat().resolvedOptions().timeZone` або еквівалент).
- **FR-4.2** Користувач з іншого пояса бачить ту саму сітку **зі зсувом**: слот 10:00–10:30 за Києвом для користувача в Берліні відображається як 09:00–09:30.
- **FR-4.3** Якщо пояс користувача відрізняється від офісного, інтерфейс явно показує це (наприклад, підпис із поясом офісу поруч із сіткою).
- **FR-4.4** Перевірки робочих годин при цьому виконуються за часом офісу (тобто «робоче вікно» на сітці користувача може бути зсунуте, напр. 08:00–18:00 у Берліні).

### FR-5. Створення бронювання

- **FR-5.1** Користувач обирає: кімнату, дату, час початку, час кінця; вводить назву бронювання.
- **FR-5.2** Правила валідації (усі — обов'язково на сервері):
  - **FR-5.2.1** Назва обов'язкова, від 1 до 100 символів.
  - **FR-5.2.2** Час початку і кінця кратний 30 хвилинам.
  - **FR-5.2.3** Тривалість: від 30 хвилин до 4 годин включно.
  - **FR-5.2.4** Бронювання лише в робочі години (09:00–19:00 за часом офісу).
  - **FR-5.2.5** Бронювання лише в майбутньому (час у минулому — відмова).
  - **FR-5.2.6** Бронювання не може перетинатися з наявним у тій самій кімнаті.
  - **FR-5.2.7** Бронювання впритул **не конфліктують**: кінець одного може збігатися з початком іншого. Приклад: 10:00–11:00 і 11:00–12:00 — два коректні бронювання.

#### Формалізація правила перетину (основа для юніт-тестів)

Інтервали трактуються як напіввідкриті `[start, end)`. Два бронювання A і B в одній кімнаті конфліктують тоді й лише тоді, коли:

```
A.start < B.end && B.start < A.end
```

Наслідки:
- `A.end == B.start` → конфлікту немає (впритул);
- часткове перекриття → конфлікт;
- повний збіг → конфлікт;
- один інтервал усередині іншого → конфлікт;
- бронювання в сусідні дні → конфлікту немає.

### FR-6. Помилки бронювання

- **FR-6.1** Якщо бронювання створити не можна, користувач бачить зрозуміле повідомлення з конкретною причиною: слот зайнятий / поза робочими годинами / час у минулому (та інші порушення правил FR-5.2).
- **FR-6.2** Перевірки виконуються на сервері, а не лише у формі. Клієнтська валідація — допоміжна, серверна — джерело істини.

### FR-7. Скасування бронювання

- **FR-7.1** Користувач може скасувати **своє** бронювання.
- **FR-7.2** Чуже бронювання скасувати не можна: ні через інтерфейс, ні прямим запитом до API (серверна перевірка власності, очікувана відповідь — 403).

### FR-8. Мої бронювання

- **FR-8.1** Окрема сторінка зі списком бронювань поточного користувача; дві секції або вкладки:
  - **FR-8.1.1** **Майбутні**: найближче зверху; у кожного — кнопка скасування.
  - **FR-8.1.2** **Минулі**: останнє зверху; з пагінацією або підвантаженням (infinite scroll / «показати ще»).
- **FR-8.2** Рядок списку показує: дату, час, кімнату і назву бронювання.
- **FR-8.3** Час, як і скрізь, відображається в поясі користувача.
- **FR-8.4** Клік по рядку веде до сітки відповідної кімнати на відповідний тиждень.

### FR-9. Редагування бронювання

- **FR-9.1** Користувач може редагувати **своє** бронювання: кімнату, дату, час початку, час кінця, назву.
- **FR-9.2** Чуже бронювання редагувати не можна: ні через інтерфейс, ні прямим запитом до API (серверна перевірка власності, очікувана відповідь — 403).
- **FR-9.3** До оновлених значень застосовуються **всі** правила валідації FR-5.2 (кратність 30 хв, тривалість, робочі години, майбутній час, відсутність перетинів).
- **FR-9.4** У перевірці перетинів саме́ бронювання, що редагується, виключається з набору наявних (інакше воно конфліктувало б саме із собою).
- **FR-9.5** Редагувати можна бронювання, яке ще не завершилося (та сама умова, що й для скасування, — див. DEC-7). Завершені та скасовані бронювання редагуванню не підлягають.
- **FR-9.6** Помилки редагування показуються так само, як помилки створення (FR-6).

## 5. Вимоги до інтерфейсу (UI)

Очікується продуманий інтерфейс, а не «форма поверх бази».

- **UI-1** Єдиний стиль на всіх екранах: відступи, типографіка, кольори. Підхід до стилів будь-який (Tailwind, CSS-модулі тощо).
- **UI-2** У кожного екрана є стани **завантаження**, **порожнечі** та **помилки**: «немає бронювань», недоступний сервер і порожня сітка не виглядають як білий екран або вічний спінер.
- **UI-3** У формах помилки показуються **біля відповідних полів**; кнопка відправки блокується на час запиту.
- **UI-4** У сітці візуально виділені **поточний день** і **поточний час**.
- **UI-5** Свої бронювання в сітці візуально відрізняються від чужих.
- **UI-6** Скасування бронювання підтверджується: діалог підтвердження або можливість скасувати дію (undo).
- **UI-7** Верстка не ламається на різних ширинах екрана. Повноцінний мобільний сценарій — бонус (BONUS-8), але деградувати верстка не повинна.

## 6. Технічні вимоги

- **TECH-1** Мова: **TypeScript** (фронт і бек).
- **TECH-2** Фронтенд: **React** або **Next.js**.
- **TECH-3** Бекенд: **NestJS**, **Express** або **API-роути Next.js** — на вибір.
- **TECH-4** База даних: **PostgreSQL**, **MySQL** або **SQLite** — на вибір.
- **TECH-5** Сітка розкладу верстається **самостійно** (таблиця або CSS grid). Готові календарні компоненти на кшталт FullCalendar **заборонені**: ця верстка й логіка — частина завдання.
- **TECH-6** Час зберігається у форматі **UTC**.
- **TECH-7** Паролі зберігаються хешованими: **bcrypt** або **argon2**.
- **TECH-8** Сіди:
  - кімнати (наприклад «Акваріум», «Марс», «Гагарін») — 5–6 штук з поверхом і місткістю;
  - два тестові користувачі (облікові дані — в README);
  - кілька демо-бронювань.
- **TECH-9** Юніт-тести на логіку перетину інтервалів; обов'язкові кейси:
  - впритул (кінець == початок) → не конфлікт;
  - часткове перекриття → конфлікт;
  - повний збіг → конфлікт;
  - сусідні дні → не конфлікт.
  Запуск: `npm test`.
- **TECH-10** Секрети й налаштування — в env; у репозиторії лежить **`.env.example`**.

## 7. Бонусні вимоги (додаткові бали)

- **BONUS-1** Docker compose, що піднімає все однією командою.
- **BONUS-2** Підтвердження email у dev-режимі: реальний SMTP не потрібен, посилання підтвердження виводиться в лог сервера; **до підтвердження бронювати не можна**.
- **BONUS-3** Щотижневі повторювані бронювання (наприклад «щовівторка, 8 повторень») зі скасуванням одного повторення або всієї серії.
- **BONUS-4** Захист від гонки: два користувачі одночасно натискають «забронювати» на один слот → у базі рівно одне бронювання. Обране рішення (транзакція, exclusion constraint, унікальний індекс, блокування тощо) описується в README.
- **BONUS-5** Сповіщення про кінець бронювання:
  - якщо наступний слот у цій кімнаті зайнятий, автор поточного бронювання за N хвилин до його кінця отримує сповіщення в застосунку (дзвіночок або тост);
  - сповіщення приходить **рівно один раз**;
  - сповіщення **не приходить**, якщо будь-яке з двох бронювань скасоване;
  - N задається через env (`NOTIFY_BEFORE_MINUTES`), за замовчуванням 10 хвилин.
- **BONUS-6** Інтеграційні тести API: створення і скасування бронювання, відмови валідації.
- **BONUS-7** Фільтр кімнат за місткістю.
- **BONUS-8** Повноцінний мобільний сценарій: сіткою зручно користуватися на телефоні.

## 9. Критерії оцінювання

| Критерій | Вага |
|---|---|
| Працює за списком «Що має працювати» (FR-1…FR-8) | 40 |
| Якість коду: читабельність, структура, відсутність сміття і мертвого коду | 25 |
| UI/UX: очікування розділу «Інтерфейс», ясність сітки, загальна акуратність | 20 |
| README та історія комітів | 15 |

- Бонусні пункти додають бали **зверху**.
- Учасник має бути готовий пояснити будь-яку частину свого коду: після перевірки можливий дзвінок з питаннями «чому написано саме так».
- **Дискваліфікація** без виставлення балів: здача чужого рішення під своїм іменем, участь із двох і більше акаунтів, змова між учасниками.

## 10. Додаткові уточнення (ухвалені рішення)

Пункти, які в ТЗ прямо не визначені. Рішення нижче ухвалені й обов'язкові до виконання нарівні з рештою вимог.

- **DEC-1** Перегляд розкладу без входу недоступний. «Зайняті слоти видно всім» означає «всім автентифікованим користувачам»; увесь застосунок — за логіном, неавтентифікованому доступні лише реєстрація та вхід.
- **DEC-2** Перший день тижня в сітці — понеділок за замовчуванням, але значення **конфігурується** (env/налаштування, напр. `WEEK_START_DAY`), щоб можна було перемкнути на неділю без правок коду.
- **DEC-3** «Лише в майбутньому» = час **початку** бронювання строго пізніший за поточний момент на сервері в момент створення.
- **DEC-4** Редагування бронювання **входить в обсяг робіт** — див. FR-9.
- **DEC-5** Скасування реалізується як **soft delete** (позначка «скасоване» + час скасування), а не фізичне видалення: це зручніше для BONUS-5 (перевірка «скасоване»). Скасовані бронювання зникають із сітки та списків і не беруть участі в перевірці перетинів.
- **DEC-6** Усі перетворення часу виконуються через IANA-timezone-бібліотеку (напр. `date-fns-tz` / `luxon` / `Temporal`), а не через фіксований офсет — так перехід на літній/зимовий час у `Europe/Kyiv` (коли «робоче вікно» в UTC зсувається) обробляється коректно автоматично.
- **DEC-7** Скасувати можна бронювання, яке ще **не завершилося** — зокрема й те, що вже почалося. Те саме правило діє для редагування (FR-9.5).
- **DEC-8** Навігація тижнями без жорсткого ліміту вперед і назад.
